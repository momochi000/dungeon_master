** game state
This is the object which represents the current state of the game (durr).
Who the player(s) is(are) (character sheets), current location, game history (user input and llm responses etc), what is the current game mode, etc.

it's structure is important and likely to be updated frequently. I must document it well.
*** structure
Record with the following fields:
+ mode
  The current game mode:
  + normal
    player is interacting with the dungeon master normally, i.e. dm is explaining the story or what the player sees/experiences
  + challenge
    player has to roll to test some action or make a saving throw
  + combat
  + dialogue (hypothetical)
    this is currently part of normal mode but this could conceivably be a discrete mode all it's own
+ world-state
  a placeholder for the output of the graph db.

  Eventually we can serialize the game entirely to an object, compress that, and
  write it to disk. This is then our saved game. part of that is dumping the
  graph db to some object, which will go here.
+ working-memory
  Things that come up during the current turn which affect how the turn is evaluated.
  for example:
  + the results of querying the knowledge base
  + the output of whether the player must make a saving throw
  + the output the player's current action intention
    e.g. player says: "I want to check the room for traps"
    LLM is consulted for a function call which returns "check traps" and determines the challenge rating. This information goes into the working memory.

    as the turn evaluates, it looks into this working memory and detects that it needs to prompt the player for a roll. The rules engine is then consulted to determine whether success or failure which is also added to working memory. Success or failure would be the outcome of this turn and upon next turn, the game detects this and the dm is prompted accordingly to describe the outcome of the action.

    the more i think this through the more it sounds like a state machine...

+ player-sheet
